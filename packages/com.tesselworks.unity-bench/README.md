# Unity Bench package

This dependency-free Editor package supplies batch workload registration and explicit result protocol v1. A consuming project registers an `IWorkload` factory from an `[InitializeOnLoad]` constructor. `Prepare` establishes frozen inputs outside the clock; `Execute` performs the complete fixed operation; `CaptureProof` computes input/output fingerprints and nonnegative finite work counters outside the clock.

`UnityBench.Editor.BatchEntry.Run` requires an explicit batch request, runs one first iteration followed by the requested warm iterations, rejects changed work/output between iterations, and emits a new UTF-8 result file. Time is `executeWallTime` in milliseconds. It measures synchronous execution wall time, not whole-process CPU time, complete Editor startup, continuous Play Mode or rendering. Asynchronous operations, initial import, script reload, Play transition and Player scenes need separate lifecycle adapters and are not implemented by this entry point.

The environment reports the actual `Application.unityVersion` and detected managed Editor backend (`mono`, `coreclr`, or `unknown`). It does not infer backend from the variant name or requested compiler flags. External validation must refuse unknown or unexpected runtime identity before making a comparison.

Receipts include the actual process ID, SHA-256 of the complete request file bytes, and echoed `sourceRevision`/`planDigest`. These echoes tie a receipt to its controller request; source checkout identity still requires independent controller verification. Actual settings include batch mode, vSync count, target frame rate and quality level. Public worker-count and code-optimization APIs are reflected without introducing package dependencies; missing APIs are explicitly unavailable/null. No physics settings or frame workload are inferred from this synchronous CPU example.

Controlled host observation requires all four request paths: `readyPath`, `startPath`, `finishedPath` and `releasePath`, plus `handshakeTimeoutSeconds` (1–120), `sourceRevision` and `planDigest`. All paths must be distinct absolute paths that do not exist. An `EditorApplication.update` coordinator first waits for actual `isCompiling: false` and `isUpdating: false`, calls workload preparation once, yields one update, and waits again for actual Editor idle. Both idle phases share one 120-second preparation bound. It then atomically writes `{runId,processId,requestSha256,utc,isCompiling,isUpdating}` to ready and yields to Editor updates while waiting for a matching start signal. After measurement and proof validation, it writes the completed receipt, atomically writes finished, and yields to Editor updates while waiting for release before exiting. The controller must atomically write matching run/PID/request-byte-digest signals with aware UTC timestamps. Start/release holds request one 50 ms cooperative sleep per update callback when the actual Editor flags are idle, then return to the Editor loop. This prevents an unmeasured idle batch loop from consuming a full core; active compilation/import does not receive this idle throttle. Both hold throttling and readiness waits are outside the operation measurement clock. Actual `environment.settings.idleHoldPollingDelayMs` records this fixed protocol delay; scheduler overshoot is not asserted to be bounded to exactly 50 ms. This is not the old blocking signal loop: every callback returns and Editor services continue between callbacks. The Editor idle flags are checked again before starting work; a busy Editor at start fails without adopting samples. The controller separately establishes its host CPU preparation window before writing start. A wrong identity, malformed signal or timeout fails the process; a completed receipt followed by a release failure is not eligible because its process exit failed. The controller owns full-lifetime CPU/memory observations and admission checks. Ordinary lifecycle-free measurement requests are refused. Result `startedUtc` and `completedUtc` bound the operation/proof region; per-sample stopwatch values remain the actual timed metric. Finished `utc` and `completedUtc` equal the result completion UTC exactly.

A failure receipt has `status: failed`, empty fingerprints/counters/samples, and process exit 1. No incomplete timing is eligible. Invalid requests may exit without a receipt because their output destination is not trusted. Existing receipts are never overwritten. Exception payloads are excluded from normal output.

This private preview has no public license grant. Runtime/Player adapters are outside this package scope. Native Editor compatibility must be established by the selected revision’s actual Unity CI; a .NET stub check is not Unity compilation.

An explicit `preparationOnly: true` request requires `warmIterations: 0`, no lifecycle paths, and the same source/plan provenance. It prepares, waits for the actual Editor idle flags via the same bounded update coordinator, executes the full workload once, validates proof and writes `status: prepared` with no timing samples. It uses no measurement stopwatch. Its UTC boundaries describe preparation only. The controller must validate this compatibility/cache prime separately and exclude it from comparisons; it is not a lifecycle-free measurement shortcut. Ordinary requests still require all four lifecycle paths.
